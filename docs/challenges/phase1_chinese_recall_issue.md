# Phase 1 真实挑战记录：中文查询召回失败

## 1. 问题背景

在 Phase 1 中，我实现了一个最小 RAG MVP：

用户问题
→ 加载 `data/docs/*.md`
→ 文档切分
→ BM25 检索
→ 返回 citation
→ 保存 trace

单元测试通过后，我使用 CLI 进行真实查询测试：

```text
上传PDF后检索不到内容怎么办？
结果系统返回：

没有在知识库中找到足够依据，建议转人工或补充更多信息。
Citations:

这说明虽然测试通过，但真实用户查询没有召回到对应文档 rag_upload_troubleshooting.md。
2. 问题表现

测试结果：

3 passed

但真实 CLI 查询失败：

请输入用户问题：上传PDF后检索不到内容怎么办？
没有在知识库中找到足够依据，建议转人工或补充更多信息。
Citations:

这暴露出一个典型工程问题：

单元测试过于理想化，真实中文查询没有覆盖。
3. 定位过程

排查后发现，当前 BM25 tokenizer 对中英文混合文本不友好。

原始查询是：

上传PDF后检索不到内容怎么办？

知识库文档中对应表达是：

上传 PDF 后检索不到内容

由于用户输入中没有空格，旧 tokenizer 容易把连续中文和英文混合内容切成较粗粒度 token，导致 query token 和 document token 匹配失败。

也就是说，问题不在 RAG 流程本身，而在：

中文 + 英文缩写 + 无空格输入场景下的分词策略。
4. 根因总结

根因是 BM25 依赖 token 匹配，而 MVP 阶段的 tokenizer 没有充分考虑中文查询习惯。

真实用户通常不会输入：

上传 PDF 后检索不到内容怎么办？

而是会输入：

上传PDF后检索不到内容怎么办？

这导致测试集和真实输入之间存在分布差异。

5. 解决方案

我将 tokenizer 改为适配中英文混合文本：

英文和数字按词切分；
中文按单字符切分；
保留对 API、PDF、Key 等英文缩写的匹配能力；
避免因为用户没有输入空格导致召回失败。

核心思路：

英文/数字：word-level token
中文：character-level token

这样可以提高中文无空格查询下的 BM25 召回稳定性。

6. 回归测试

为避免同类问题再次出现，我补充了一个真实失败场景测试：

上传PDF后检索不到内容怎么办？

测试目标：

必须召回 rag_upload_troubleshooting.md

这使得该问题从一次临时修复变成了可持续验证的 regression test。

7. 项目经验总结

这个问题让我意识到：

单元测试通过不等于真实查询可用；
RAG 系统不仅要看 pipeline 是否跑通，还要看真实用户表达能不能召回；
中文场景下，BM25 的 tokenizer 设计会显著影响召回质量；
对 Agent/RAG 项目来说，trace、失败样例和 regression test 比单纯功能实现更重要。
8. 面试表述

在 Phase 1 中，我遇到过一个真实 RAG 召回问题：单元测试全部通过，但 CLI 中输入“上传PDF后检索不到内容怎么办？”时，系统没有召回到对应的排查文档。定位后发现问题不是 RAG 流程，而是 BM25 tokenizer 对中文和英文缩写混合、且无空格输入的场景处理不好，导致 query token 和文档 token 匹配失败。

我没有简单地修改测试用例，而是调整 tokenizer 策略：英文和数字按词切分，中文按字符切分，并补充了 no-space 中文查询的回归测试，确保后续类似“上传PDF”“APIKey失效”这类真实用户输入也能稳定召回。这个问题让我认识到，RAG 项目不能只看 demo 是否跑通，还要关注真实查询分布、召回失败定位和 regression test。
